The Architecture of Agent Skills: Context Windows as Ephemeral Filesystems

February 18, 2025 · 6 min read

When function calling arrived in production LLM APIs in mid-2023, it felt like an unambiguous triumph of systems engineering. By constraining model decoding across a strict JSON Schema grammar, providers turned non-deterministic token streams into deterministic remote procedure calls. We gave the model an array of tool signatures, the model emitted {"name": "fetch_user", "arguments": {"id": 42}}, and orchestrators dutifully dispatched the request over HTTP.

For trivial applications—a weather widget, a calculator, a database lookup—this abstraction holds. But as soon as you attempt to build an autonomous systems engineer—an agent capable of triaging a failing Kubernetes cluster, navigating a multi-gigabyte monorepo, refactoring an observability pipeline, and verifying its own changes—the monolithic function-calling paradigm collapses under its own design assumptions.

The failure is architectural: we have treated the context window as an API gateway when it is actually an ephemeral CPU cache.

"Programs must be written for people to read, and only incidentally for machines to execute." — Harold Abelson, Structure and Interpretation of Computer Programs

To scale agents beyond toy workflows, we must abandon static schema inlining and return to first principles of operating system design. Capabilities should not be baked into the prompt envelope as rigid JSON schemas. They must be structured as dynamic, discoverable skills residing in an ephemeral filesystem—paged into working memory on demand, composed via standard POSIX primitives, and executed within hardened sandboxes.

The Context-Window Token Tax and Attention Diffusion

Consider what happens when an enterprise agent is equipped with sixty discrete tools across Git, AWS, Jira, Datadog, and PostgreSQL. In the standard tool-use pattern, the JSON Schema definitions for all sixty operations are serialized into the system prompt on every single inference turn: 

{
  "tools": [
    {
      "name": "cloudwatch_get_metric_data",
      "description": "Retrieves batched metric data points from AWS CloudWatch...",
      "parameters": {
        "type": "object",
        "properties": {
          "MetricDataQueries": { "type": "array", ... },
          "StartTime": { "type": "string", "format": "date-time" },
          "EndTime": { "type": "string", "format": "date-time" },
          "ScanBy": { "type": "string", "enum": ["TimestampDescending", "TimestampAscending"] }
        },
        "required": ["MetricDataQueries", "StartTime", "EndTime"]
      }
    },
    ... 59 other exhaustive schemas ...
  ]
}

This schema dump immediately extracts a crushing double penalty:

  • Economic and Latency Overhead: Sixty schemas easily devour between 10,000 and 25,000 prompt tokens. In a complex, 40-step trajectory, you are transferring, caching, and attending over hundreds of thousands of tokens of static capability descriptions that may never be invoked. Even with aggressive KV-cache prefix optimization, time-to-first-token (TTFT) and throughput degrade noticeably.
  • Attentional Diffusion: Far more insidiously, inlining schemas compromises model reasoning. Multi-head self-attention computes a normalized softmax distribution over the key sequence:
    αi,j = exp((qi · kj) / √dk) ∑m=1N exp((qi · km) / √dk)
    When the prompt is flooded with thousands of syntactic boilerplate tokens—types, field descriptions, enums, nested object brackets—the attention mass is dispersed across irrelevant distractor tokens. This induces parameter hallucinations, tool confusion (calling query_db_v2 instead of run_sql), and diminished recall for the user's actual constraints.

Progressive Disclosure: The Context as L1 Cache

Computer systems solve capacity and latency trade-offs through memory hierarchies: registers feed into L1/L2/L3 caches, which page against RAM, which in turn maps backing stores on NVMe drives. A CPU core does not load the entirety of secondary storage into its register files before executing an instruction; it maintains page tables and pulls cache lines upon demand.

Human engineers work identically. When dropped into a million-line code repository, no engineer reads all 4,000 header files before starting. Instead, they scan the root directory, read the top-level README.md, identify the relevant subsystem, and inspect specific implementations only when a task demands it.

An Agent Skill mirrors this exact mechanism through progressive disclosure. Rather than injecting exhaustive parameter trees into the root context, skills are encapsulated as directory trees within a local filesystem: 

.agents/
├── catalog.json              # Tier 0: Shallow index (~200 tokens)
└── skills/
    ├── k8s-triage/
    │   ├── SKILL.md          # Tier 1: Semantic specification & CLI guide
    │   └── scripts/
    │       └── dump_pod_logs.sh  # Tier 2: Encapsulated implementation
    └── postgres-explain/
        ├── SKILL.md
        └── explain_query.py

Execution proceeds across three explicit architectural tiers:

  • Tier 0 (Shallow Catalog): The agent's permanent system context contains only a compact summary table of available skill names and one-line summaries. The cost is negligible: 50 skills consume fewer than 400 tokens.
  • Tier 1 (Demand Paging): When the agent recognizes that a cluster incident requires pod diagnostics, it reads .agents/skills/k8s-triage/SKILL.md via standard file inspection. The detailed operational manual—flags, environment variables, edge cases—is loaded into the context window precisely when the model is ready to act.
  • Tier 2 (Execution & Eviction): The skill invokes an underlying executable. Once the diagnostic phase concludes, subsequent context compression or sliding-window summarization evicts the detailed skill specification, restoring attentional bandwidth for the next phase of the plan.

Sandboxed Execution vs. The RPC Trap

The function-calling paradigm inherited the worst impulses of enterprise Service-Oriented Architecture: treating every operation as a discrete, rigid RPC endpoint. But rigid RPC endpoints are fundamentally anti-compositional.

Consider a typical systems task: an agent needs to locate an error pattern in a service log, extract unique correlation IDs, and query an internal service for customer metadata. Under the discrete RPC model, the agent must invoke three separate tools across multiple round-trips: 

Turn 1: call get_service_logs(service="auth", limit=1000)
        -> returns 4MB of raw JSON containing 1,000 entries into context.
Turn 2: model attempts to parse 4MB JSON in-context, hits context limit or drops tokens.
Turn 3: call lookup_user_by_id(user_ids=[...]) for 40 users individually.

Every byte of intermediate telemetry is forced to travel across the inference boundary, burning tokens and polluting working memory.

Contrast this with granting the agent access to a sandboxed POSIX execution shell (such as a Linux container with unshare isolation, cgroups v2, and a read-only root with an ephemeral overlay). The agent solves the problem using classic Unix philosophy: 

journalctl -u auth.service --since "30 min ago" \
  | grep "ERROR: auth_failed" \
  | awk -F'correlation_id=' '{print $2}' \
  | awk '{print $1}' \
  | sort -u \
  | head -n 10 \
  | xargs -I{} ./scripts/lookup_metadata.sh {}

The architectural difference is profound: data aggregation and transformation occur off-context in operating system memory. Four megabytes of raw unstructured text are filtered down to eight concise lines of output before touching the model's tokenizer.

Furthermore, shell execution provides natural self-correction loops. When a JSON schema call fails because an argument is malformed, the orchestrator returns an opaque schema validation error. When a shell command fails, standard streams provide high-bandwidth, descriptive diagnostics: non-zero exit codes, compiler tracebacks, and stderr hints. Because frontier LLMs are trained on billions of lines of shell interactions and debugging sessions, they resolve a syntax error or a missing flag in a bash pipeline with vastly higher fidelity than a proprietary REST error schema.

Determinism, Idempotency, and Verification Gates

The inherent risk of autonomous agent execution is state pollution: partial execution, race conditions, or unrecoverable mutations triggered by hallucinated parameters. If an agent executes three destructive steps and fails on the fourth, the system is left in an undefined, corrupted state.

Robust agent skill design demands two strict systems invariants:

  • Idempotency by Construction: Any skill that mutates persistent state must implement idempotency keys or declarative convergence (similar to Terraform or Kubernetes reconcilers). Re-running apply_patch or deploy_revision with identical inputs must yield identical state without side-effect amplification.
  • The Verification Gate: Execution must be bifurcated into distinct propose, sandbox verify, and commit phases. State modifications should target copy-on-write scratch environments (such as Git staging branches or Docker overlay filesystems). The orchestrator runs automated test suites, linters, or type-checkers against the scratch environment before any commit transaction is promoted to production.

Designing Software for Synthetic Consumers

For half a century, software interfaces have been designed for two distinct audiences: human operators (who value graphic ergonomics, intuitive naming, and visual affordances) and machine-to-machine integrations (which value rigid, strongly typed binary contracts like gRPC or ASN.1).

Autonomous reasoning agents represent a radically different third consumer: an entity with fluid general reasoning, high semantic parsing capacity, but bounded working memory and zero tolerance for token bloat.

When designing APIs for this new class of synthetic consumers, the architectural rules invert:

  • Maximize Semantic Density per Token: Avoid verbose, deeply nested JSON payloads where keys outweigh values. Compact, self-describing formats (such as clean TSV, Markdown tables, or terse YAML) frequently outperform sprawling JSON schemas in both token efficiency and parser reliability.
  • First-Class --help Interfaces: Command-line tools that print concise usage examples and clear error messages when invoked with invalid arguments provide immediate on-ramp guidance without requiring static prompt pre-loading.
  • Return to Plan 9's Filesystem Ethos: Exposing system state as a hierarchy of virtual files and directories allows agents to leverage their most refined reasoning muscles: navigating trees, reading slices of files, and piping streams.

Conclusion: The Operating System of Thought

The transition from static function-calling JSON schemas to filesystem-backed agent skills is not merely an ergonomics improvement; it is an architectural necessity. Monolithic tool dumps treat large language models as fragile pattern matchers that must be spoon-fed every parameter constraint upfront.

By treating the context window as a dynamic, volatile CPU cache over a sandboxed filesystem, we align agent architectures with the proven principles of computing history: hierarchical caching, progressive discovery, composable POSIX interfaces, and sandboxed verification. The future of autonomous systems will not be built on brittle API wrappers, but on the enduring foundation of operating systems primitives.
