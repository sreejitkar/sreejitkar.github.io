The Economics of Inference: Memory Bandwidth, Disaggregation, and the KV Cache Tax

November 9, 2025 · 8 min read

The technology industry spent three years captivated by the spectacle of training runs: 100-megawatt clusters, tens of thousands of GPUs stitched together with optical transceivers, and nine-figure checks written to converge trillions of parameters over months of sustained compute. Yet in the ledger of technology economics, training is an amortized capital expenditure. You write the check once, capitalize the asset, and amortize it across the expected commercial lifetime of the model checkpoint.

Inference, by contrast, is a perpetual operational expenditure. It is an unyielding, per-query toll levied by the laws of semiconductor physics. Every prompt processed and every completion token generated consumes physical kilowatt-hours, occupies high-bandwidth memory (HBM), and competes for interconnect cycles.

Traditional enterprise SaaS enjoyed gross margins of 75% to 85% because serving bytes over NGINX or executing an indexed read on a PostgreSQL replica cost a fraction of a millicent. In generative workloads, that margin structure implodes. When an autonomous agent executes a 50-step loop—ingesting tool descriptions, parsing documentation, and emitting reasoning traces—software ceases to behave like frictionless code and begins to behave like industrial manufacturing. The economics of modern software are no longer dictated by software architecture alone, but by memory bus throughput, cache residency, and hardware scheduling.

"Training creates capability; inference dictates viability. A model you cannot afford to serve at scale is indistinguishable from a model that does not work."

The Roofline Model: Why Decoding Starves the GPU

To understand why serving large language models is economically punishing, one must examine the system through the lens of the Roofline Model (Williams, Waterman, and Patterson). The model bounds achievable operational performance (P) as a function of arithmetic intensity (I), defined as floating-point operations performed per byte transferred from dynamic memory: 

Operational Intensity (I) = FLOPs / Memory Traffic (Bytes)

P_achieved = min( P_peak,  I * Bandwidth_mem )

Consider an NVIDIA H100 SXM5 accelerator. It provides approximately 989.5 TFLOPS of dense FP16/BF16 Tensor Core compute and 3.35 TB/s of HBM3 memory bandwidth. Dividing peak compute by memory bandwidth yields the hardware's critical inflection threshold: 

I* = 989.5 * 10^12 FLOPs/sec / 3.35 * 10^12 Bytes/sec
   ~ 295.4 FLOPs / Byte

If a kernel executes fewer than ~295 floating-point operations for every byte it fetches from HBM, execution is strictly memory-bandwidth bound. The multi-thousand arithmetic logic units inside the Streaming Multiprocessors (SMs) spend the majority of their clock cycles stalled, waiting for memory controllers to deliver operands across the silicon interposer.

Transformer inference bifurcates violently across this threshold into two entirely distinct workloads:

  • Prefill (Prompt Processing): In prefill, the engine processes all prompt tokens Sin concurrently. The projection layers (Wq, Wk, Wv, Wo) and MLP feed-forward projections operate as large General Matrix-Matrix multiplications (GEMM). For an input batch of size B and sequence length S, each weight loaded from HBM into on-chip SRAM is reused across B × S tokens. Arithmetic intensity scales directly with sequence length (I ∝ B × S). When B × S > 300, arithmetic intensity comfortably surpasses I*. The GPU runs in the compute-bound regime, achieving 50% to 65% Model FLOPs Utilization (MFU).
  • Decode (Token Generation): Because autoregressive generation produces tokens sequentially—token t conditioned on t-1—the active token sequence length per stream is strictly S = 1. The matrix multiplications collapse into General Matrix-Vector products (GEMV). To emit a single token, every single parameter of the model must be streamed from HBM into registers, multiplied by a single activation vector, and discarded.

For an unbatched stream (B = 1), the arithmetic intensity of decode is roughly: 

I_decode = (2 * Parameters * 1) / (Parameters * Precision_Bytes)
         = 2 / 2  (for FP16)
         = 1.0 FLOP / Byte

At I = 1.0 FLOP/Byte, the H100 achieves less than 0.35% of its theoretical compute capacity. The SMs are starved. The minimum physical latency to emit a single token for a 70-billion parameter model in 16-bit precision (140 GB of weights) distributed across two H100 GPUs (2 × 3.35 TB/s = 6.70 TB/s) is bounded entirely by the memory bus: 

Latency_step >= (140 * 10^9 Bytes) / (6.70 * 10^12 Bytes/sec)
             ~ 20.9 milliseconds per token (~47.8 tokens/sec)

It does not matter whether the node has 1,000 TFLOPS or 10,000 TFLOPS of compute available. Until the memory bus can stream the 140 gigabytes of weights across the interposer, the next token cannot be sampled.

The KV Cache Tax: The Space-Time Bargain

To avoid recomputing attention across all preceding tokens at every autoregressive step—an O(S2) compute penalty per token—serving engines maintain a Key-Value (KV) Cache. By caching the projected key and value activation tensors at every transformer layer, the marginal compute per step drops to O(S).

This algorithmic bargain trades compute for memory footprint. The memory consumed by the KV cache scales linearly with sequence length, batch size, and layer count according to the exact relation: 

Memory_KV = 2 * L * n_kv * d_head * S * B * P_bytes

Where:
  L       = Number of Transformer layers
  n_kv    = Number of Key/Value attention heads
  d_head  = Hidden dimension per head (d_model / n_heads)
  S       = Total sequence length (prompt + completion)
  B       = Concurrent batch size
  P_bytes = Precision in bytes (2 for BF16/FP16, 1 for FP8)

Consider a modern frontier-class open model like Llama 3 70B (L = 80, nq = 64, nkv = 8 via Grouped-Query Attention, dhead = 128): 

Bytes per token per sequence (BF16):
  = 2 * 80 * 8 * 128 * 2 bytes
  = 327,680 bytes ~ 320 KB / token

While 320 kilobytes per token appears benign in isolation, observe how the memory ledger compounds across production context windows:

  • At 4,096 tokens: 320 KB × 4,096 = 1.28 GB per active request.
  • At 32,768 tokens: 320 KB × 32,768 = 10.24 GB per active request.
  • At 131,072 tokens (128k context): 320 KB × 131,072 = 40.96 GB per active request.

Now consider the economics of an 8x H100 SXM5 server node (8 × 80 GB = 640 GB total HBM). The FP16 weights of Llama 3 70B consume roughly 140 GB. Tensor parallel activations and runtime scratchpad memory reserve another ~20 GB, leaving approximately 480 GB of unfragmented HBM for the KV cache pool.

If users execute requests within a 32k context window, that entire $300,000 server node can host at most: 

Max Concurrency = 480 GB / 10.24 GB ~ 46 concurrent requests

At request 47, the cluster is out of memory. The engine must either reject the request, queue it behind high head-of-line latency, or preempt active requests by swapping their KV pages to host system RAM over PCIe Gen5. But PCIe Gen5 x16 provides only ~64 GB/s bi-directional bandwidth—nearly 50 times slower than on-board HBM3. Memory swapping destroys token streaming rates, plunging inter-token latency from 25 ms into hundreds of milliseconds.

The Monolith Crumbles: Prefill/Decode Disaggregation

Historically, LLM serving engines—such as baseline vLLM or TensorRT-LLM—adopted a monolithic topology. Every GPU worker within a tensor-parallel replica handled both prefill and decode tasks. To interleave both workloads, modern schedulers employ iteration-level continuous batching with chunked prefill (e.g., Sarathi-Serve).

Under real-world multi-tenant traffic, this colocation creates severe operational interference:

  • Decode Jitter and SLA Degradation: When a client submits an 8,000-token prompt, the prefill GEMM kernel consumes the entire SM array for 150–300 milliseconds. Any active decoding streams packed into that same iteration cycle are blocked from emitting their next token. To the end user or client agent, output streaming freezes, inducing unacceptable Time-Between-Tokens (TBT) tail latencies.
  • Hardware Misallocation: Prefill wants raw compute density—massive FLOP throughput to burn through matrices. Decode wants memory bandwidth and vast memory capacity to hold hundreds of KV cache streams. Forcing both phases onto the same uniform silicon compromises both.

This friction has driven the rise of Prefill/Decode (P/D) Disaggregation (implemented in architectures like Splitwise, DistServe, and Mooncake). 

[ Ingress Request Router ]
           |
   +-------+-------+
   | (Prompt Phase)
   v
[ Prefill Worker Pool ]  ---> Compute-optimized nodes (H100 / B200)
   |                          High MFU (55-70%), saturated Tensor Cores
   |  (KV Cache Transfer via
   |   400 Gbps RDMA / RoCEv2)
   v
[ Decode Worker Pool ]   ---> Bandwidth- & capacity-optimized nodes
                              Saturated memory bus, zero prefill interference
   | (Autoregressive Stream)
   v
[ Client SSE Stream ]

In a disaggregated architecture, prefill workers process the initial prompt at near-peak MFU, compute the initial KV tensors, and then transfer the KV state over a dedicated high-speed network fabric (such as 400G RoCEv2 or InfiniBand) directly into the HBM of a decode worker via Remote Direct Memory Access (RDMA).

Is the network transfer cost tolerable? Let us run the numbers. For an 8k prompt on Llama 3 70B, the KV cache footprint is 8,192 × 320 KB ≈ 2.56 GB. Across a dual-rail 400 Gbps RDMA fabric (2 × 50 GB/s = 100 GB/s real wire throughput): 

Transfer Time = 2.56 GB / 100 GB/sec = 25.6 milliseconds

Because this transfer occurs concurrently with the sampling of the first token, the network latency is virtually invisible to the user's Time-To-First-Token (TTFT). Meanwhile, the decode pool operates with clockwork determinism, maintaining 20–25 ms per-token generation without experiencing prefill latency shocks.

The Arsenal of Mitigation: Algorithmic and Systems Relief

The software industry cannot wait for hardware manufacturers to double HBM capacity every eighteen months. A battery of systems and algorithmic techniques has emerged to alleviate the memory bottleneck:

1. Virtual Memory for Tensors: PagedAttention

Prior to the development of PagedAttention (Kwon et al., vLLM), serving engines allocated contiguous memory buffers for a sequence's KV cache based on its maximum possible sequence length (Smax). Because real-world generation lengths are stochastic, this resulted in staggering memory waste: 60% to 80% of GPU HBM was lost to internal and external fragmentation.

PagedAttention mirrors the virtual memory architecture of modern operating systems. The KV cache is partitioned into fixed-size physical blocks (typically 16 or 32 tokens). A logical page table maps continuous token positions to non-contiguous physical memory pages allocated on demand. Fragmentation falls to sub-4%, immediately tripling effective serving concurrency on identical silicon.

2. Architectural Attention Distillation: MQA and GQA

In classic Multi-Head Attention (MHA), every query head has a distinct key and value head (nkv = nheads). For a 64-head model, this requires storing 64 key vectors and 64 value vectors per token.

Grouped-Query Attention (GQA) partitions query heads into groups that share a single key-value head. In Llama 3 70B, 64 query heads are grouped across 8 KV heads—an 8x reduction in KV cache size and memory traffic compared to standard MHA, with negligible degradation in model perplexity.

3. KV Cache Quantization (FP8 and INT4)

While model weights are often compressed using post-training quantization, quantizing activations dynamically is harder due to outlier channels. However, moving the KV cache from BF16 (16 bits) to FP8 (E4M3 or E5M2 formats, 8 bits) halves the cache footprint immediately, doubling batch capacity with imperceptible perplexity loss.

Advanced techniques such as KIVI decompose key and value matrices along different dimensions: quantizing keys per-channel and values per-token down to INT4 (4 bits). This delivers a 75% reduction in KV memory overhead, dropping the Llama 3 70B cache footprint to just 80 KB per token.

4. Radix Tree Prefix Caching

In agentic architectures, RAG pipelines, and multi-turn conversational systems, prompts share extensive redundant prefixes: system instructions, OpenAPI tool definitions, few-shot examples, and ingested reference documents.

Engines like SGLang and vLLM organize the KV cache pool as a Radix Tree (trie) keyed on token sequences. When an incoming prompt matches an existing node in the tree, the engine skips the prefill GEMM operations entirely, referencing the existing physical KV pages via copy-on-write pointers. A prefix cache hit drops Time-to-First-Token from seconds to single-digit milliseconds and drives the marginal compute cost of the prompt to zero.

5. Speculative Decoding: Trading Compute to Bypass Bandwidth

Speculative decoding (Leviathan et al.) exploits the core premise of the Roofline Model: since the decode phase has excess compute capacity but is throttled by memory bandwidth, we can spend surplus FLOPs to reduce memory passes.

A lightweight "draft" model (e.g., a 1B or 8B parameter variant) rapidly generates K candidate tokens at low latency. The large target model (e.g., 70B) then evaluates all K candidates simultaneously in a single forward pass. Because evaluating K tokens in parallel is a compute-intensive GEMM operation rather than a memory-bound GEMV, the target model verifies the candidate tokens using the same memory bus pass it would have spent generating a single token. If M tokens are accepted (M ≤ K), latency per generated token drops by 2× to 3× without altering the model's output distribution.

The Economic Endgame: The Unit Economics of Autonomous Agents

The shift from conversational chatbots to autonomous agents fundamentally breaks naive inference cost models.

In a simple chat query, the token exchange is O(1): a single prompt of 1,000 tokens yields a completion of 400 tokens. At standard commercial API rates ($2.50 per million input tokens, $10.00 per million output tokens), each query costs ~$0.0065.

In an autonomous software engineering agent (e.g., executing a ReAct loop to locate a bug, modify code, run test suites, and inspect failures), the workload is an iterative state machine spanning dozens of cycles. Crucially, the prompt context compounds monotonically: 

Step 1:  System Prompt + Problem Statement                ~ 3,000 tokens
Step 2:  History + File Tree + Grep Output                 ~ 8,000 tokens
Step 10: History + File Diffs + Test Run 1 Failures        ~ 28,000 tokens
Step 25: History + Stack Traces + Second Attempt           ~ 65,000 tokens
Step 50: History + Final Verification Run                  ~ 110,000 tokens

Because the entire historical context must be re-evaluated at each step k, total prompt tokens ingested over an N-step trajectory scale quadratically: 

Total Prompt Tokens = ∑_{k=1}^N S_k  ~  O(N²)

For a 50-step agent loop averaging 40,000 tokens of context per step, the agent consumes: 

50 steps * 40,000 tokens/step = 2,000,000 prompt tokens

Without prefix caching, that single agent invocation costs $5.00 in input tokens alone. If the task fails 50% of the time and requires a retry, the blended cost per successful software task escalates to $10.00–$15.00. For an enterprise SaaS provider charging $30 to $50 per user per month, just three or four complex agent tasks per seat will consume the entire subscription revenue, plunging gross margins into negative territory.

With Radix prefix caching, however, step k reuses the exact KV cache state of step k − 1. The engine only pays prefill FLOPs for the newly appended tool output (perhaps 1,500 tokens). Total ingested tokens drop from 2,000,000 to less than 80,000—a 96% reduction in operational cost.

Coupled with P/D disaggregation, which prevents long-context agent prompts from degrading interactive user queries, and FP8/INT4 KV quantization, which allows servers to maintain concurrency under 100k+ contexts, the unit economics of autonomous software flip from impossible to profitable.

The Physics Behind the Balance Sheet

It is tempting to view artificial intelligence purely through the lens of statistics: loss landscapes, attention heads, and parameter counts. But at production scale, software is bound by physical constraints.

The balance sheets of the next generation of software companies will not be won solely by the elegance of their prompts or the fine-tuning of their weights. They will be determined by whether their systems engineers understand the Roofline Model, how aggressively their serving stack tames the KV cache tax, and how efficiently their clusters disaggregate prefill compute from memory-bandwidth decoding.

In the final accounting, intelligence is cheap to conceive, but expensive to stream. The systems architecture of inference is the ultimate arbiter of who survives the transition from AI demonstration to economic utility.
