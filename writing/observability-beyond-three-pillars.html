Observability Beyond the Three Pillars: Wide Events and Dynamic Sampling

October 14, 2024 · 7 min read

For nearly a decade, engineering organizations have structured their telemetry around a comforting theological trinity: metrics, logs, and distributed traces. The industry erected specialized vendors, open-source standards, and operational rituals around these so-called “three pillars of observability.” Yet, when a complex distributed outage strikes at 3 A.M., the ritual invariably breaks down.

An engineer stares at an anomalous p99 latency spike on a Grafana dashboard. They open a log aggregator to query the time window, only to drown in millions of unstructured string lines. They attempt to extract a correlation ID, switch tabs into a tracing backend, and discover that the trace for the offending request was discarded by a naive 1% head-based sampling rule. The engineer spends the next two hours manually reconstructing causal state by stitching together disconnected clocks, partial error messages, and educated guesses.

The failure here is not operational incompetence; it is an architectural category error. Metrics, logs, and traces are not fundamental laws of computation. They are lossy, accidental artifacts born from historical storage hardware constraints. By treating them as isolated silos, we have engineered systems that are both financially ruinous to operate and structurally incapable of answering novel questions about production behavior.

"Observability is not the act of collecting metrics, logs, and traces. It is the mathematical property of a system that allows you to infer its internal state purely from its external outputs — especially states you never anticipated."

The Cardinality Wall: Why Time-Series Databases Fracture

The structural deficiency of traditional monitoring begins with the time-series database (TSDB). Systems like Prometheus, M3DB, and InfluxDB were architected for infrastructure telemetry — tracking CPU utilization, memory residency, network packet counters, and disk I/O queues. In this domain, the set of monitored entities is bounded by machine counts.

A TSDB defines a distinct time series by its metric name combined with an exact set of label key-value pairs: 

series_id = hash(metric_name, {k_1=v_1, k_2=v_2, ..., k_n=v_n})

Prometheus maintains an inverted index (postings lists) mapping every unique label pair to 32-bit internal series IDs. The active series are kept in memory within head chunks before being compacted into immutable two-hour blocks on disk. The mathematical catastrophe occurs when engineers attempt to apply TSDBs to application-level debugging by introducing high-cardinality identifiers: 

http_request_duration_seconds_bucket{
  endpoint="/v1/checkout",
  tenant_id="org_84920",
  user_id="usr_993812",
  deployment_id="sha_4f10c3"
}

The total series space $|S|$ is governed by the Cartesian product of the distinct value sets for each label dimension: 

|S| = |Endpoints| × |Tenants| × |Users| × |Deployments| × |Buckets|

With 10,000 tenants and 1,000,000 users, $|S|$ explodes into hundreds of millions of ephemeral time series. The inverted index term dictionary explodes in memory. Compactor routines (compactor.go) running merge-sort passes thrash the OS page cache, trigger runaway heap allocations, and inevitably collapse under the Linux Out-Of-Memory (OOM) killer.

To prevent these crashes, platform teams enforce draconian metric-linting rules: drop user_id, strip tenant_id, and sanitize high-cardinality tags at the gateway. But in doing so, we commit telemetry mutilation. The exact dimensions required to isolate a customer-specific fault, a corrupted payload, or an account-level deadlock are stripped away before data ever touches disk.

The Unified Wide Event Paradigm

To move beyond the cardinality wall, we must discard the idea of emitting fragmented telemetry mid-flight. Instead of spraying twenty logger.info() statements and twenty incrementing counters across a request handler, a service should construct a single, comprehensive, structured record: a canonical wide event.

A wide event represents the complete lifecycle of an execution unit (an HTTP request, a Kafka consumer batch, a background job) emitted precisely once upon completion. It is a deeply dimensional JSON or Avro object containing 50 to 300 contextual attributes accrued during execution: 

{
  "timestamp": "2024-10-14T11:42:08.194821Z",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "parent_span_id": "5fb397be34d23b0f",
  "service": "billing-engine",
  "environment": "production",
  "region": "us-east-1",
  "az": "us-east-1a",
  "http": {
    "method": "POST",
    "route": "/v1/invoices/:invoice_id/charge",
    "status_code": 504,
    "duration_ms": 2841.12,
    "client_ip": "198.51.100.42",
    "user_agent": "Stripe-Webhook/v2"
  },
  "app": {
    "tenant_id": "org_enterprise_9918",
    "customer_tier": "tier_1",
    "invoice_id": "inv_9981248",
    "currency": "EUR",
    "amount_cents": 45000000,
    "feature_flags": ["use_v2_settlement", "instant_payout_hold"]
  },
  "db": {
    "query_count": 14,
    "total_duration_ms": 194.2,
    "slowest_query_ms": 178.4,
    "lock_wait_ms": 12.1
  },
  "downstream_rpc": {
    "payment_gateway": {
      "target": "acquirer-eu.internal:443",
      "duration_ms": 2500.04,
      "error": "deadline_exceeded",
      "retries": 2
    }
  },
  "runtime": {
    "alloc_bytes": 1492080,
    "gc_pause_ns": 412000,
    "goroutines": 482
  }
}

Notice what this accomplishes. We no longer need separate metrics, logs, and traces. The wide event subsumes all three:

  • Metrics become queries: Calculating p99 latency for a tenant is merely a projection: SELECT quantile(0.99)(duration_ms) FROM events WHERE tenant_id = 'org_enterprise_9918'.
  • Traces become causal joins: Rebuilding the call tree is a simple filter: SELECT * FROM events WHERE trace_id = '4bf9...' ORDER BY timestamp ASC.
  • Logs become fields: Error details, debug fingerprints, and internal state are native attributes on the record, preserved alongside the customer ID and network socket timings.

Context Propagation and Interceptor Mechanics

Building wide events requires context to flow uninterrupted through execution runtimes and network boundaries. In-process, this relies on execution-scoped context trees. In Go, the standard library provides context.Context; in Java, Project Loom introduces ScopedValue (replacing the leak-prone ThreadLocal); in Node.js, AsyncLocalStorage hooks the V8 microtask queue.

Rather than mutating raw context pointers across internal boundaries, we inject an accumulator pattern into the root request context: 

package telemetry

import (
    "context"
    "sync"
    "time"
)

type EventAccumulator struct {
    mu         sync.Mutex
    attributes map[string]any
    startTime  time.Time
}

type ctxKey struct{}

func WithAccumulator(ctx context.Context) (context.Context, *EventAccumulator) {
    acc := &EventAccumulator{
        attributes: make(map[string]any, 64),
        startTime:  time.Now(),
    }
    return context.WithValue(ctx, ctxKey{}, acc), acc
}

func AddField(ctx context.Context, key string, val any) {
    if acc, ok := ctx.Value(ctxKey{}).(*EventAccumulator); ok {
        acc.mu.Lock()
        acc.attributes[key] = val
        acc.mu.Unlock()
    }
}

Across service boundaries, context propagation relies on the W3C Trace Context and W3C Baggage specifications. The traceparent header conveys causal coordinates (version, trace ID, parent span ID, trace flags): 

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
baggage: tenantId=org_enterprise_9918,tier=enterprise,datacenter=us-east-1

However, distributed baggage carries a hidden runtime tax. OpenTelemetry interceptor pipelines that naively serialize and forward arbitrary baggage headers introduce memory allocation churn on the critical RPC path. Furthermore, uncontrolled baggage growth can exceed HTTP reverse-proxy buffer limits (such as Envoy’s default header size limits or Nginx’s 8KB large_client_header_buffers), triggering catastrophic cascading 431 Request Header Fields Too Large errors under load.

Production-grade systems must implement strict baggage whitelisting and byte-budget enforcement at ingress proxies, rejecting or pruning unapproved tags before propagating headers downstream.

Dynamic Sampling: Escaping the Head-Based Trap

A production cluster handling 100,000 requests per second generates 8.64 billion wide events per day. Storing every single event without sampling is economically indefensible. Yet traditional head-based sampling is mathematically toxic to incident investigation.

In head-based sampling, the decision to retain or discard a trace is made at the edge proxy (such as Envoy or an API Gateway) at the instant of arrival, typically by hashing the trace ID: 

if (crc32(trace_id) % 100) < sample_rate_percent {
    retain_trace();
}

The fundamental flaw of head-based sampling is epistemic blindness: at the moment of ingress, the proxy cannot know whether the request will succeed in 12ms, time out after 5,000ms, or hit a PostgreSQL serialization failure. If you sample at 1%, you drop 99% of your errors and 99% of your latency tail. You are left blind precisely where visibility is most critical.

Tail-Based Sampling Pipelines

The remedy is tail-based dynamic sampling. Instead of making sampling decisions at ingress, the decision is deferred until the transaction terminates and all participating spans have finished.

Spans are streamed to a dedicated cluster of OpenTelemetry Collectors running the tailsamplingprocessor. The collector maintains an in-memory ring buffer holding incomplete traces for a sliding evaluation window (e.g., 10 to 30 seconds). Once the trace completes or the window expires, a multi-rule evaluation engine inspects the complete graph: 

processors:
  tail_sampling:
    decision_wait: 10s
    num_traces: 50000
    expected_new_traces_per_sec: 2000
    policies:
      # 1. Deterministic error retention: Keep 100% of failures
      - name: retain-errors
        type: status_code
        status_code: { status_codes: [ ERROR ] }

      # 2. Tail latency retention: Keep all p99.5 outliers
      - name: retain-slow-traces
        type: latency
        latency: { threshold_ms: 1500 }

      # 3. Canary and enterprise tenant retention
      - name: retain-high-value-tenants
        type: string_attribute
        string_attribute:
          key: app.customer_tier
          values: [ "tier_1", "vip" ]

      # 4. Adaptive downsampling for mundane traffic
      - name: sample-normal-traffic
        type: probabilistic
        probabilistic: { sampling_percentage: 0.1 }

Tail sampling transforms the economics of observability: 100% of anomalies, crashes, deadlocks, and slow paths are captured, while boring, repetitive 200 OK traffic is reduced by 99.9%.

The core distributed systems challenge in tail sampling is trace routing. Because spans belonging to a single trace are generated by multiple disparate microservices, they must be routed to the identical collector node evaluating the sampling policy. This requires a two-tier collector architecture: an ingress tier of stateless agents hashing the trace_id (e.g., via consistent hashing with Murmur3) to forward spans to a partition-keyed cluster of tail-sampling stateful workers.

Storage Primitives: Lucene vs. Modern Columnar Engines

Where should wide events live? For the past decade, log analytics was dominated by the Lucene inverted index (Elasticsearch, OpenSearch). Lucene was designed for full-text search: tokenizing prose, maintaining term frequencies, and computing BM25 relevance scores.

When used as a telemetry sink for wide events containing 150 structured attributes, Lucene suffers catastrophic write amplification:

  • Index bloat: Lucene generates inverted index postings, term dictionaries (.tim), term indexes (.tip), and doc values (.dvd) for every single indexed attribute. A 1 TB collection of raw events frequently expands to 2.5 to 4 TB of disk footprint.
  • LSM merge thrashing: Background segment merging burns substantial CPU cycles constantly rewriting sorted term lists on disk, causing heavy GC pauses on the JVM heap.

Modern observability infrastructure has decisively shifted toward vectorized columnar engines, with ClickHouse, DuckDB, and specialized analytical formats (Parquet on object storage) leading the migration.

The ClickHouse Storage Model

In a columnar engine, wide events are stored column-by-column rather than row-by-row. If an analytical query only aggregates duration_ms grouped by tenant_id, the engine scans strictly those two physical files, bypassing the remaining 148 attributes entirely. 

CREATE TABLE telemetry.wide_events
(
    timestamp          DateTime64(6, 'UTC') CODEC(DoubleDelta, ZSTD(1)),
    trace_id           FixedString(32)      CODEC(ZSTD(3)),
    span_id            FixedString(16)      CODEC(ZSTD(3)),
    parent_span_id     FixedString(16)      CODEC(ZSTD(3)),
    service            LowCardinality(String),
    environment        LowCardinality(String),
    tenant_id          LowCardinality(String),
    customer_tier      LowCardinality(String),
    route              LowCardinality(String),
    http_status        UInt16               CODEC(T64, ZSTD(1)),
    duration_ms        Float64              CODEC(Gorilla, ZSTD(1)),
    db_query_count     UInt32               CODEC(T64, ZSTD(1)),
    db_duration_ms     Float64              CODEC(Gorilla, ZSTD(1)),
    error_message      String               CODEC(ZSTD(6)),
    attributes         Map(String, String)  CODEC(ZSTD(3))
)
ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (environment, tenant_id, service, route, toUnixTimestamp(timestamp))
SETTINGS index_granularity = 8192;

This schema demonstrates the mechanics that allow columnar engines to outclass Lucene by an order of magnitude:

  • Specialized column codecs: Timestamps use DoubleDelta, compressing sequential timestamps down to single bits per row. Durations utilize Gorilla floating-point compression. Repeated categorical strings use LowCardinality dictionary encoding. The overall compression ratio routinely exceeds 10:1 to 14:1 relative to uncompressed JSON.
  • Sparse primary indexes: Rather than indexing every row, ClickHouse creates a sparse index entry once every 8,192 rows (an index granule). Binary search locates the granule bounds, after which the engine uses SIMD vector instructions (AVX-512) to scan and filter millions of records per core per second.
  • Ad-hoc arbitrary slicing: Because column reads are isolated, operators can filter or group by any arbitrary dimension — even high-cardinality keys like user_id or deep nested JSON paths — without pre-planning index keys or triggering memory exhaustion.

The Unified Telemetry Plane

The consolidation of telemetry is not merely a vendor optimization or cost-saving measure; it changes how engineers develop mental models of their distributed systems in production.

When we eliminate the artificial boundary between metrics, logs, and traces, we eliminate the context-switching tax that cripples incident response. The question is never “which dashboard has the right metric?” or “which search string matches the log file?” The question is simply: What changed across the execution trajectories of our requests?

By emitting rich, structured canonical wide events at unit-of-work boundaries, managing volume through intelligent tail-based dynamic sampling, and persisting records into SIMD-accelerated columnar stores, we reclaim the original promise of observability: the ability to understand any emergent failure state — no matter how bizarre, unprecedented, or complex — without having had the foresight to predict it in advance.
